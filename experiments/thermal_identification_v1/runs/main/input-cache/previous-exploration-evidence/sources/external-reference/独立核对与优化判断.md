# TTO短问答、基础曲线与0.2.2关键源码：独立核对

日期：2026-10-13。范围：上传短问答报告、曲线JSON、可恢复的原始记录及与本次数据相关的源码链。没有修改生产代码、访问设备、训练模型或推送仓库。

## 1. 结论

1. 本次实际覆盖的是约1.54～3.16秒的单路短文本请求。六条稀疏请求均出现接近峰值的PWM在请求结束后仍保留约31～33秒的行为；随后才逐步下降。回到请求前PWM+1个百分点以内，首次观测约为结束后73.7～83.7秒。短请求有明显调节尾巴的担忧得到支持。
2. 没有出现80%～100%高档位、连续问答使gain不断增加或PWM失控爬升。连续组PWM主要在约32%～41%，任务前TJ上升约1°C后并非单调增长。不能描述成已发生热控失控。
3. 值得优化的是AUTO额外风量的退出条件及原响应学习如何解释负载结束；不先降低用户基础曲线、不直接设低PWM上限、不让最初若干秒一律不响应。
4. 报告与原始数据的主要统计一致。但本文仅是数据与关键源码核对，不是0.2.2全量软件发布放行或温控效果验收。
5. 两批长/短记录已经值得用于Ridge参照和低阶灰箱探索；不必为此再次重跑同样实验。模型的跨过程/跨硬件有效性、降低风量后的温度和听感，仍未证明。

温度正在从刚才的局部峰值下降，但相对较早低温的30秒斜率仍可为正。参考源码的`allow_down`要求guard≤90°C且斜率无效或非正；若条件不满足，较低需求会被保留为当前PWM。条件满足以后才应用差额式退档和0.3pp/s的慢尾。

因此，数据与源码共同强烈支持“先被长窗口退档条件挡住，再开始限速回落”的解释。不是固定的‘每题保温30秒’计时器，也不能把它解释成已准确估计整块铝仍需42%散热。当前函数不直接读取请求完成、GPU使用率或功率。

接收采样间隔造成首峰出现在结束后0.6～2.7秒，不能单靠该亚秒/秒差断言控制程序晚启动。更可靠的现象是持续约30秒的平台和后续几十秒尾巴。

## 5. 基础曲线：先不改，先认清现场使用哪一份

用户文件：30°C→0%、40→10%、50→15%、55→25%、60→35%、65→40%、70→45%、80→50%、90→60%；普通min10%、max100%，hysteresis2°C，min_interval1000ms。

按文件40～50°C线性段和参考源码整数插值，本轮44～49°C对应基础需求约12%～14%，而观测峰值37%～42%。AUTO还含升温附加、gain和输出历史限制，不能把这37%～42%直接归因于基础曲线，也不能把基础曲线百分比当成已验证的安全档位。

此外，文件尚不能代替实机配置回读。按S01首个峰值的温度48.5°C、斜率6.6°C/min、gain1.77526以及参考源码低温分支计算，文件给出的即时未限速需求约37%，而API输出42%。输出受历史保持和未采到的控制周期影响，这个差异**不是**单点证明配置错误；但也不足以声称已用这份文件精确复现了现场控制。需要取得本次实际fan.config及其与固件的对应关系后再调参数。

参考实现中，hysteresis/min_interval用于CURVE路径，AUTO有独立趋势、学习和限速规则。不要为了30秒AUTO平台去盲改JSON的1秒间隔或2°C回差。

最小后续核对是已授权现场只读导出当前实际配置并登记与本轮是否相同，不重跑负载、不先应用这份文件；若只能取得现在的配置，明确不能倒推历史。

## 6. gain：确有规则更新，不等于热参数已学准

原始记录出现8次变化，每次新值/旧值约0.95：1.8686947→1.7752599→1.6864969→1.6021720→1.5220634→1.4459602→1.3736621→1.3049790→1.2397300。

参考源码的update_response_learning在观察结束后，用前后温度斜率差决定gain乘1.15或0.95。它没有分辨“任务结束导致发热降低”和“风扇增速带来的冷却贡献”。本轮每条稀疏短请求自然结束后降温，与该减益分支相符。

因此可以说现有控制在按规则自适应，不能说它识别了真实热阻、热容量或散热效率。长负载轮上调、短问答轮下调，说明任务形态及控制历史会影响增益；这不是自动证明系数应被清零或学习功能应立刻关闭。

优化时应分别评估：允许额外风量更及时退出；gain更新是否需要区分负载变化/测量资格。不要用统一乘小gain来掩盖退档许可问题。若试固定gain，应先是离线对照候选，未经另行授权不改现机。

本次查看了0.2.2的profiles、platform_quality、platform_engine、features、model、collector及修复交付说明等关键链路。明确有Orin/Thor平台分组、Thor的独立rail和NVML字段、AUTO/CURVE资格区别；记录程序没有向风扇写入控制。旧Orin字段不能代替Thor解释。

当前模型起点最多每5秒一次、历史180秒、输出15/45/90秒。按保存的325个起点，18条正式请求中只有8条请求的客户端执行区间含预测起点，10条没有。并不代表采集丢了这些任务：1610份新温度及原始输入均在。后续针对短脉冲建模应使用完整原始时间序列，并显式报告事件周边预测覆盖，不只使用5秒预测表或总体均值。是否改变起点节奏是下一次实验设计问题，不要求现在重做采集。

多数正式任务小于3秒，说明这轮覆盖较短脉冲；不能宣称全部3～10秒、长上下文多轮或图片推理都已经验证。但这些数据足以支持本次拖尾观察，无须为偏短而全部作废。

## 8. 红叉与恢复：只记影响，不调查根因

按用户优先级，不调查通讯/刷新冲突、不新增故障测试、不修改失温策略。D12后设备明确报告stale并改变输出，该事件与仅TTO读不到响应不同。保留异常及控制恢复影响，不能用其后快速降档证明AUTO正常退档已经改善；也不因此删除整个run。
