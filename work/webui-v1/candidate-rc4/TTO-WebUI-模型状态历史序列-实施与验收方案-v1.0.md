## 2. 当前问题与必要决策

现有 `state.py` 只缓存 metrics 历史，模型输出仅存在于当前快照。直接把当前模型值追加到每次发布或每次请求上，会把后续传播后的状态错误地配给旧 TJ；三条序列各自抽样，还会让前端无法在同一采样上计算差值。因此同时解决“何时取值”和“联合请求怎样保留同一行”，不能只增加三个 id。

采用以下决策：

1. 仅以新合格 TJ 采样为数值记录入口，取同包观察器完成该次 TJ 校正后的 Tf/Ts/E。普通 tick、风扇或其他指标发布不新增模型数值点。
2. 内部保存一份 TJ/Tf/Ts/E 联合行；请求新模型序列时，对该组共同选点。旧的纯指标请求保持原有行为。
3. TJ−Tf 命名为“校正后估计残差”，不等同于校正前 `innovation_C`，也不等同于 D 区未来预测误差。由于 Tf 已吸收该次 TJ，该残差不能作为独立预测准确率证明。
4. E、Ts−E、Tf−Ts 是温度状态的代数分解，单位均为 °C；不叫热量占比、结构测温或室温。允许负差值，不截零、不绝对值、不修改模型以迎合面积图。

## 3. 数据合同

### 3.1 序列与来源

| id | 标签及类型 | 数值来源 |
| --- | --- | --- |
| `temperature.tj` | 实测结温，observed，°C | 同包合格 TJ 样本 |
| `model.Tf_C` | 快热状态估计，estimate，°C | 同包 `model.Tf_C`，校正后 |
| `model.Ts_C` | 慢热状态估计，estimate，°C | 同包 `model.Ts_C`，校正后 |
| `model.E_C` | 等效边界估计，estimate，°C | 同包 `model.E_C`，校正后 |

模型序列明确标注 `estimate_stage=posterior`、`anchor_metric_id=temperature.tj`；`phase_at_sample` 保留 tracking/degraded 的区别，不添加置信度。

数值点沿用 `t/value/status/sample_id/received_at_utc/source_ref` 的基本形状。模型点的采样标识及来源引用关联其 TJ 锚点，元数据明确这是估计的溯源关系，不是传感器读数；收到时间使用已有真实字段，不生成虚构时间。缺口点为 `value=null`，无样本时 `sample_id=null`，附可枚举的 `reason_code`。不输出 NaN/Infinity。

### 3.2 数值写入资格和时间

必须同时满足：

- 包通过现有来源、时钟域、冻结 model/spec 及单调性校验；`new_tj=true` 且该组内 TJ 样本未重复。
- TJ 有限、状态 valid，Web 接收时尚在其既有有效期内。
- 模型 phase 为 tracking 或 degraded，Tf/Ts/E 全部有限。
- 来源已连接，Web 接收时严格满足 `now < model_until`；`model_until=min(consumable_until_mono_s,TJ._expiry)`，与当前模型的实际截止规则一致。
- 观察器输出确实对应这次新 TJ 的校正时刻；TJ 时间与该包模型状态截止时间在既有发布精度内一致。若来源不能证明这一点，返回 `alignment_mismatch` 缺口，不把后来状态回填到旧时刻。

`t` 使用该 TJ 的 `as_of_elapsed_ms`，单位为相对本 run 起点的毫秒；不使用 HTTP 请求时刻、UTC 或缓存 TJ 的后来发布时刻。验收比较同一采样的 TJ 与模型状态截止时间、来源引用和值，不能只比较数组长度。

不复用预测的“每秒最多一次”门槛限制历史写入，也不新增观察器调用。只要容量允许，就记录每次合格新 TJ；重复样本、tick 和读请求不会重复追加数值。

### 3.3 缺口、恢复与已知历史

| 触发 | 模型历史行为 |
| --- | --- |
| provisional/unavailable、TJ 无效或任一状态非有限 | 进入缺口，不写模型数值 |
| `publication_gap` 或显示发布异常 | 立即形成断点；同位置冲突时缺口优先 |
| disconnect/观察结束 | 立即形成断点，停止新增模型数值 |
| 无新包且 `model_until` 到期 | 依现有期限检查形成断点，时间为既有截止时刻 |
| 恢复 | 只有新的、资格齐全且时间晚于断点的 TJ 才恢复数值 |

断连或发布异常的断点使用 Web 检测到该事件的 elapsed 时刻；阶段失效使用对应包时刻。数值行时间必须单调，显式断点不早于最后已记录行。连续失效区间只需一个断点，不随每次 refresh/request 累积重复 null；无数据时也保持有界。

已公布的断点构成历史时间屏障：若随后到达的新 TJ 源时间不晚于该断点，不在模型历史中补回数值，标记其处置原因为 `arrived_after_gap`；等待下一次晚于断点的合格 TJ。这样既不倒排时间，也不把延迟包画成跨已知断源的连续曲线。该策略只约束新增历史，不改变当前模型、预测标签或来源接收策略。

断点之前的合格历史继续保留，不能因现在 TTL 到期而整段撤销。新旧值之间不插值、不补零、不沿用旧状态；历史不用于延长当前快照有效期。阶段变为 tracking 但没有新 TJ，也不能自行恢复数值。

### 3.4 数据组身份与迟到响应

缓存属于 `(run_id,source_epoch,model_id,spec_id)`；任一变化均清空联合行、去重标识和缺口状态。Web 重启更换 `service_epoch`，历史为空，不跨进程恢复。

`/series` 响应增加完整身份 `service_epoch/run_id/source_epoch/model_id/spec_id`，与数据在同一响应生成过程中取值，避免身份和 payload 分属两个时刻。冻结模型/spec 不匹配仍按原入口拒绝，不能为了测试清空而放宽来源验证。

客户端接入合同：请求记录完整身份与请求代次；数据组切换立即清空相关历史并使旧请求失效；旧响应即使同 run、同查询参数也不得回填。后端无法撤回已经发出的 HTTP 响应，客户端检查是必要组成部分。Sonnet 接入说明及最小浏览器验证覆盖该责任，保留 rc3 的既有防护。

### 3.5 联合请求与共同抽样

主接入请求为：

```text
/api/v1/series?ids=temperature.tj,model.Tf_C,model.Ts_C,model.E_C&max_points=2000
```

出现任一 `model.*` 新 id 时，启用 `tj_model` 共同抽样组，无需增加必填查询参数：

- 三个模型序列投影自同一份联合行。若同时请求 TJ，则该 TJ 返回同一组锚点视图；元数据明确 `alignment_group=tj_model`、`time_basis=tj_sample`。单独请求 `temperature.tj` 仍返回原始指标历史，原默认 ids 不变。
- 模型不可用但该次 TJ 合格时，可保留该行 TJ 数值，三个模型值为 null。显式断源/发布断点在联合视图四列均为 null，表示曲线分段；这不撤销独立 TJ 序列中的真实记录。
- 对联合行一次确定保留索引，再投影所有被请求列；各列的 t、sample_id 和断点位置逐项一致，不能分别按极值抽样后用插值拼接。
- 保留首尾、桶内各原始分量的极值，以及 `TJ−Tf`、`Ts−E`、`Tf−Ts` 的极值；差值只在所需分量均有效时计算。共同抽样必须保留全部断点，并保留有效段边界，避免吞掉短暂恢复段。
- `max_points` 是软绘图预算：按每桶最多保留的联合索引数设置桶数；强制断点与分段边界可能使返回超预算，响应明确标记并给出原始/返回行数及实际 sampling 方法。绝对行数不超过缓存上限，不能静默丢断点来满足预算。

只请求部分模型列时，仍按同一固定四列及三个差值确定索引，避免因增减可见曲线而改变残差极值。混合请求中的功率、PWM 等旧指标沿用自身采样规则，元数据不宣称它们与 TJ 同步。

### 3.6 合同文件与兼容

在 `src/tto_web/contracts` 增加 series 响应 schema 和正常/缺口/分组切换示例；严格校验实际接口输出，覆盖未知字段策略及新增 reason/sampling 枚举。现有 dashboard schema 是快照合同，不把历史硬塞进当前快照模型字段。

bootstrap 采用新增的序列能力/目录字段公布三条模型序列及共同抽样规则；`available_fields` 保持当前 metrics 的含义。旧消费者不请求新 id 时，其点值与抽样行为不变；新增响应元数据采取兼容扩展。原始 PRD/合同资料保留，单列本次合同增量。

## 4. 低开销实现与验收门槛

实现限于现有 `State.accept/refresh/disconnect/series` 和 server 对应接口：共享小型资格判断，确保当前模型截止规则与历史资格一致；不借此重构预测、建议或采集链。

- 一份紧凑联合行 deque，`maxlen=18002`，按现有 elapsed 时间裁剪 3600000 ms 以前记录；样本率超过容量时先受容量约束，不宣称必定保存整整一小时。
- 每行只保存时间、四个值和必要来源/阶段信息；组身份及固定元数据共享。不维护三个完整 dict 历史副本，不设无界去重集合。裁剪、身份切换同时释放相关引用。
- 接收时 O(1) 追加，过期记录摊销裁剪；series 查询只扫描所请求的有界时间窗，完成一次共同抽样后再构造 JSON。空闲时不为历史重建整表，不把全量历史加入 SSE/快照，不增加轮询或常驻线程。
- 不新增数据库、依赖、进程、持久化日志或数值模型计算；复用既有期限检查和 HTTP 通路。不因显示失败阻塞原采集/观察器链，不扩大其异常传播范围。

实施后的本地预算：

| 项目 | 门槛与口径 |
| --- | --- |
| 新增历史缓存 | 饱和 18002 行时，新增存活 Python 分配 ≤16 MiB；以相同输入基线/候选差分及分配快照核对，报告来源字符串等实际占用 |
| Web 过程总量 | 延续既有 RSS 峰值 ≤192 MiB、平均 CPU ≤5% 单核等效；新增缓存预算不能代替总量预算 |
| 有界性 | 持续覆盖、裁剪、失效及身份切换后，记录数和关联索引不持续增长；请求临时分配回收后不形成常驻复制 |
| 网络与查询 | 保持既有刷新频率；记录共同请求的返回点数、响应字节及延迟，尤其披露断点密集时软预算超额，不另加自动高频请求 |

使用最终 wheel 的隔离安装，与封存 rc3 做同口径短测：合成来源、一个浏览器、相同输入和原有请求节奏；候选额外启用一次共同历史请求。先用受控时间预填饱和窗口，再各采集约 120 秒，不为填满窗口真实等待一小时。报告原始计量、主机、模式、采样时长、均值、峰值及输入速率；浏览器和原观察器成本单列，不冒充新增 Web 过程成本。

16 MiB 是本方案提出的新增上限，原因是只有一份有界四列缓存，不应消耗数十至数百 MiB。任一预算超限先定位根因并修复，不降采样/放宽 TTL 掩盖。短测如出现持续增长或时延异常，再有针对性延长；不重复无依据的多轮长跑。上述本机成绩不能外推为 N305 资源通过。

单元测试用可控时钟，不启动真实负载；联合测试经过生产的发布/接收与 HTTP 路径，故障注入留在测试替身。浏览器检查同时核对画面、请求返回、DOM/可访问性状态，覆盖缺口不连线和同 run 换 epoch 的迟到响应。后端独立验证页通过只证明接口及接入规则可用，不代表 Sonnet 新首页已验收。
