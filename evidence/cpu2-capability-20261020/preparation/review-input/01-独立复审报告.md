## 3. R2：SSH启动与退出为什么可以接受

`cpu_transport.py`的`tick`只安排后台启动任务，不再在唯一时钟循环中等SSH检查。源码固定mux检查最多1秒、启动步骤3秒、实际源启动后首包1秒；均占用既定60/1200秒，不额外延长。自身check/source子进程有登记、stderr有界保留、TERM/KILL与任务回收有限等待；没有操作SSH master的分支。

独立重新执行原23项局部测试，**全部通过**。包括真实runtime在mux检查永不返回时约0.2秒触发STOP/诊断截止，以及本地真实睡眠子进程的超时回收。测试使用自建服务/进程替身，并不是已连接真实SSH。目标机上可能缺现有mux、源解释器/路径不符或启动超过预算；这些应导致本轮失败并保留阶段证据，不能自动改超时或重新登录。

接受的是这处缺陷的实现与相关验证，不是承诺所有OS调用绝不延迟，也不是现场SSH性能已经验收。

## 4. R1：接通且不把失效数据捡回来

已重新运行完整模型`replay.py`：**14项回归通过**，实际150包wire/arrival → 唯一bridge → Activity → 原evaluate_stream成功。5份适配结果与原权威结果逐字节一致，11份派生成果的结构、引用、计数、状态一致，最大浮点差 `1.42e-14`，低于既定1e-8容差。

另用独立脚本从wire原字节/原计数核算，未用bridge自己的CPU公式作“独立”答案：

- 150包序列化内容与接收source逐包一致；146个完整稳定合法计数窗，另外4个首窗/重置/在线集切换窗退出相应资格。
- 150个CPU事件都不改变GPU/两条rail已有记录的值、来源及截止；292份有效CPU摘要支持端点不晚于真实接收时刻+1秒。
- 342个事件帧、56个原TJ决策起点；一条原接受TJ最多一个热预测起点，未造高频温度答案。
- BASE为314 ACTIVE / 28 UNKNOWN；MEAN和CORE各214 ACTIVE / 128 UNKNOWN，与作者一致。
- 原样本中的计数回退、在线集合变化及原生断连/epoch变化确实撤销资格；之后合法新窗可恢复。旧`cpu_interface`已标明弃用，其兼容查询也不再先筛invalid而复用旧valid。

这些数量说明接口和失效语义接通，不是识别准确率。只有1个合格共同15秒温度答案，45/90秒没有共同答案，是短合成样例的正常限制；本轮没有新热精度或CPU先导收益。

CPU源时钟与N305接收时钟仍分开；这次冻结的是接收顺序研究支持，**不是源采样绝对新鲜度或零传输延迟**。200ms窗每秒抽取最后一个值也不是重新计算1秒CPU积分窗。旧CORE=MEAN、新策略未胜HOLD的负结果原样保留。
