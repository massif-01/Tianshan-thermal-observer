# TTO 测试者使用说明

适用版本：TTO 0.2.0，出厂预装Conda的N305。

你用TTO做两件事：**记录设备正常使用时的温度和散热状态，查看这些记录是否适合评价预测。** 拿到真实冻结模型后，还可以观察未来15、45、90秒的温度预测。

TTO安装在N305上，风扇继续由TianshanOS控制。当前通过终端启动，结果用浏览器打开。第一次测试不需要先训练模型，也不需要安装CUDA。

## 第一次测试的路线

1. 安装TTO，确认版本为0.2.0。
2. 填写计算模块监控服务（Orin或Thor）和TianshanOS的访问地址。
3. 运行3分钟连接检查。
4. 记录一次正常使用过程。
5. 生成报告，交回完整测试资料。

**第3、4步会连接你填写的设备。** 安装后的离线检查、生成报告和打开报告都不连接设备。下面的联网命令由你在准备好的测试现场执行，不会因为填写了地址就自动开始。

## 1 先认识这套软件

| 设备或程序 | 提供什么 | 你需要知道什么 |
| --- | --- | --- |
| N305上的TTO | 保存记录、预测、生成报告 | 这是你运行命令和查看文件的电脑 |
| Orin/Thor上的rm01OrinStatus监控服务 | 芯片温度、负载、功耗 | TTO需要这个服务的访问地址 |
| ESP32上的TianshanOS | 风扇控制百分比、自动模式、保护状态、控制温度 | TTO读取WebUI背后的状态接口，浏览器不用一直开着 |

同样的功耗，风扇控制百分比不同，温度走势也可能不同，所以TTO同时记录两路数据。它读取的是已确认成功下发的风扇百分比，不把目标设定值当作实际输出。

这里的“设备地址”，技术文档有时叫“端点”，就是 `http://设备IP:端口` 这样的访问地址。

## 2 安装并确认版本

如果使用《TTO测试者使用包》，打开其中的 `TTO-v1-0.2.0-conda-install` 文件夹。如果单独下载Conda便捷安装包，先解压，再进入同名文件夹。

在Ubuntu文件管理器中进入这个文件夹，右键空白处，选择“在终端打开”（英文系统为Open in Terminal），执行：

```bash
sh install.sh
```

脚本复用出厂Conda，创建独立的TTO环境、安装依赖和程序，最后做离线检查。默认需要下载依赖；不会把TTO依赖装进Conda的base。安装完成会显示“安装完成：TTO 0.2.0”。

确认版本：

```bash
~/TTO/tto --version
```

应显示：

```text
0.2.0
```

以后都用 `~/TTO/tto` 启动，不需要手动执行 `conda activate`。重复运行安装脚本会保留配置、模型和记录。

| 安装后的文件 | 用途 |
| --- | --- |
| `~/TTO/tto` | 程序入口 |
| `~/TTO/config/local.json` | 设备地址等本机设置 |
| `~/TTO/runs/` | 每次录制生成的文件夹 |
| `~/TTO/installation.json` | 实际安装版本和程序身份，交资料时保留 |

如果安装提示找不到Conda，在已经初始化Conda的终端重试；维护者也可帮你指定预装Conda的位置。不要为此重新安装另一套Conda。离线安装和自选目录的步骤见安装包内的README。

## 自动识别与升级提示

0.2.0的新记录会从计算模块监控服务的声明自动识别Orin/Thor，不需要你选择。配置节名`orin`沿用旧版，填写Thor地址也放在这里。`unknown`表示缺少有效声明，不会根据IP或GPU字段猜平台。

监控服务配套候选为tegrastats-api 1.1.1。Thor需要可选的官方NVML绑定；TTO本身不安装CUDA、不启动负载。GPU为0%是有效空闲读数；“不可用/错误/过期”与0%分开。

安装到原`~/TTO`时，安装器支持从0.1.2 Conda环境升级，保留`local.json`、模型和记录。旧模型仍能用于旧数据离线评估；新记录只使用声明了相同平台、控制范围和输入合同的新冻结模型。不自动训练或启用模型。

`features.power_current_rails`保留为旧配置兼容字段；新版功耗列由平台自动选择，改这个旧列表不能切换新版rail。旧采样周期和网络设置继续保留。

## 3 填写设备地址

用文本编辑器打开 `~/TTO/config/local.json`。找到下面两处 `base_url`，把对应的 `null` 换成真实地址，保留双引号、逗号和其他设置。

| 所属部分 | 填谁的地址 | 怎么找到 |
| --- | --- | --- |
| `orin` 中的 `base_url` | rm01OrinStatus监控服务 | 从当前运行服务的配置确认IP与端口，或请维护者提供 |
| `tianshan` 中的 `base_url` | TianshanOS | 通常就是你打开控制网页时使用的地址 |

例如，一个地址字段改完后可能长这样：

```json
"base_url": "http://192.168.1.20:5000",
```

**这只是格式示例，IP和5000端口都不是默认值。不要照抄数字。** 两台设备分别填写各自的真实地址。

只填地址的开头部分，例如 `http://192.168.1.30`。如果控制网页地址后面有 `/index.html`、`#/fan` 等页面路径，去掉这些部分。不用手填 `/api/v1/fan/status` 或 `/socket.io`，程序已经知道这些接口。

### 源采样周期怎么填

`orin` 部分还有两个字段：`source_sample_interval_ms` 和 `source_interval_evidence`。它们记录计算模块监控服务（Orin或Thor）**实际多久产生一份新采样**，不是要求你改变服务频率。

新版监控服务会直接发布实际源周期，TTO自动读取；可以保留这两项为null。只有仍使用明确旧合同、且维护者确认当前源服务确实每1秒采样一次时，才把原文件中的两行分别改为：

```json
"source_sample_interval_ms": 1000,
"source_interval_evidence": "已核对源服务生效配置：1000ms",
```

不知道时，两项保留 `null`。仍可记录原始数据，但模型预测资格暂不可用；交回资料时写“源采样周期未确认”。不要凭网页刷新速度、端口或经验猜周期，也不用改其他轮询参数。

### 检查编辑有没有出错

保存文件后执行：

```bash
~/TTO/tto doctor --config "$HOME/TTO/config/local.json"
```

这是离线检查。看到下面两个字段表示配置格式通过，**还没有连接设备**：

```json
"status": "offline_config_valid",
"connected": false
```

如果提示配置错误，先检查双引号、逗号和字段所在位置。地址为空时，离线检查也可以通过；下一步联网前必须填好两个真实地址。

设备需要登录认证时，请维护者配置本机认证文件；不要把账号密码塞进URL，也不要把认证文件打包交回。

## 4 做一次3分钟连接检查

确认两路源服务已运行、N305能访问它们，再执行：

```bash
~/TTO/tto doctor --config "$HOME/TTO/config/local.json" --live --duration 180
```

**这条命令会连接设备，计划只读观察180秒，到时停止并收尾。** 权限、数据或资源问题可能使它提前结束；它会保存这一轮已经写下的原始记录。

| 终端提示 | 怎么理解 |
| --- | --- |
| 已连接，正在等待第一份有效温度数据。 | 通道连上了，还要等有效新测量 |
| 数据暂不可用，预测已暂停。 | 当前没有可用新数据，不能把旧缓存当新采样 |
| 本轮TTO已停止；现有风扇控制未被修改。 | 本轮观察结束 |

终端不是每秒刷新，有时安静一段时间是正常的。最终输出是一组JSON文字，不需要逐项读懂；先找 `run`、`new_samples` 和 `observer_stop_reason`。

- `run`：这次录制的完整文件夹路径，后面生成报告要用。
- `new_samples`：有效新测量数量。大于0说明收到过新测量，不等于整段数据都可靠或模型有效。
- `observer_stop_reason`：正常跑满时间是 `duration`，按Ctrl+C停止是 `SIGINT`。

收到数据也不能自动证明现场装的是正确源服务版本。源服务最终安装包与生效配置仍需现场核对；未确认的地方在测试记录里写“未确认”。

## 5 记录一次正常使用过程

连接检查后，按设备原有方式正常使用。不要为了测试额外启动负载、修改风扇曲线、温度绑定或采样频率。

下面记录30分钟，场景名叫“办公使用01”：

```bash
~/TTO/tto collect --config "$HOME/TTO/config/local.json" --duration 1800 --episode "办公使用01"
```

这条命令会联网。`1800`是秒数，等于30分钟。尽量覆盖自然升温、正常使用和后续降温；按实际完整过程选择时长，单次最多4小时。

**场景名用来说明是不是同一个持续过程。** 同一过程因时长限制分两次录制，沿用同名；已经结束、下一次独立使用过程，换成“办公使用02”等新名字。不要把每个文件都当成独立实验，也不要随意把不同过程起成同名。每次测试在记录模板里说明起止情况。

没有模型也可以执行 `collect`，数据与简单参考预测会照常记录。第一次测试先把数据记录好即可。

### 怎样提前停止

在运行TTO的终端按一次 **Ctrl+C**，等到“本轮TTO已停止”再关闭终端。它停止的是观察程序，已有风扇控制继续运行。

看到 `SIGINT` 或 `SIGTERM` 是正常停止方式。其他停止原因、磁盘不足、授权失败或队列丢弃需要留在测试记录中。不要删掉该轮数据，也不要重启设备或源服务来替代问题记录。

## 6 生成报告并用浏览器打开

录制结束后，找到终端里的 `run`。复制双引号中的完整路径，用它替换下面第一行的 `这里替换为本次run完整路径`。

```bash
RUN="这里替换为本次run完整路径"
REPORT="$HOME/TTO/reports/$(date +%Y%m%d-%H%M%S)"
~/TTO/tto report --run "$RUN" --output "$REPORT"
xdg-open "$REPORT/report.html"
```

这几行只读本机已有记录，**不连接设备**。Ubuntu会用默认浏览器打开报告；也可以在文件管理器里找到对应的 `report.html`，双击打开。

每次报告需要新目录。上面的命令用时间生成新名称；若提示目录已存在，不要删除旧报告，等一秒重新生成新名称即可。

报告目录中有三份内容相同、用途不同的文件：

| 文件 | 用法 |
| --- | --- |
| `report.html` | 用浏览器看，测试者优先看这份 |
| `report.md` | 可编辑的文字版 |
| `report.json` | 完整数字、原因和原始引用，给维护者复核 |

## 7 报告先看什么

### 普通采集报告

用 `collect` 录制后，主要看采集质量：

| 项目 | 你要判断什么 |
| --- | --- |
| 有效新测量 | 是否真正收到新数据 |
| 连接质量和缺口 | 有无断线、缓存、冲突、过期或丢弃 |
| 正常AUTO/CURVE起点 | 当时风扇与温度来源是否符合评价条件 |
| 停止原因 | 是否按时或手动结束，还是因异常提前停止 |
| 资源与记录时长 | 本轮在这台N305上的运行情况，是否覆盖你要记录的过程 |

“正常AUTO/CURVE起点”不是原始采样总量。风扇非自动模式、处于保护或故障、温度失效或来源不符合要求等，都可能使这个数很低或为0。把当时情况照实写下来，不要为了增加数量改风扇或绑定设置。源采样周期未确认还会使模型预测不可用，这与正常AUTO/CURVE状态计数是两项检查。

普通采集报告没有正式模型成绩是正常的。软件能记录，不代表已经证明预测有收益。

### 旁路预测报告

拿到真实冻结模型并用下一节的 `shadow` 录制后，报告还会显示当时实际发出的预测与保存的评分。先看“计划起点、已发、历史评分、质量排除、当前有效”，再看误差。

| 报告里的方法名 | 中文含义 |
| --- | --- |
| `persist` | 假设温度维持当前值的简单参考 |
| `trend30` | 按最近温度走势给出的简单参考 |
| `ridge_tj` | 使用温度历史的小模型，简称M0 |
| `ridge_full` | 还使用风扇、负载、功耗等输入的小模型，简称M1 |

| 指标或状态 | 怎么理解 |
| --- | --- |
| MAE | 平均绝对误差，单位℃；只在同一评分集合内比较才公平 |
| RMSE | 对较大误差更敏感的误差指标，单位℃ |
| 绝对误差P95 | 约95%分位的绝对误差，帮助看大多数误差的上沿 |
| 欠预测 | 预测低于后来实际温度，观察时尤其留意 |
| 过预测 | 预测高于后来实际温度 |
| 降级 | 缺少部分输入后只用了较简单的方法，不算M1成功 |
| 未能评分 | 没有合适的未来标签、跨段、尚在等待或证据缺失；不等于误差0 |

旁路报告里，各方法可用的起点不一定相同，不能拿两行MAE直接断定哪个模型更好。正式判断模型价值，要看单独离线评估报告里的共同评分集合。

**覆盖率要和误差一起看。** 同一方法、同一时距的主表覆盖率，是“当前有效评分 / 当时计划起点”。例如计划100个起点、当前只有60条可用评分，覆盖率就是60%；被质量隔离的历史部分仍在分母里。另有按该方法已发预测计算的评分率，详见JSON。

“历史评分”表示当时确实保存过，“当前有效”表示现在仍适合用于评价。后来出现同身份读数冲突或序号倒退，受影响的旧片段会退出有效误差和图，原始记录保留；后续恢复的有效片段继续计分。不要为了消除警告删整轮或编辑评分文件。

已有预测需要等到对应未来时刻才能评分。第一条预测发出后，15、45、90秒的成绩不会同时立刻出现；软件结束时尚未等到未来温度的预测，也可能保留为未评分。

看到“模拟”时，这些数字只用于熟悉软件流程，不是实机成绩。一轮旁路表现也不能替代独立时间留出评估；不要根据某个漂亮误差表决定降低风扇百分比。

## 8 拿到真实模型后再做旁路观察

这一步不是第一次记录的前置条件。等待维护者提供准备使用的真实冻结模型，在TTO目录中新建 `models` 文件夹，把模型放进去并保留原文件名；不要用模拟演示模型连接真机。

下面假设文件叫 `真实冻结模型.json`。先做离线检查：

```bash
~/TTO/tto doctor --config "$HOME/TTO/config/local.json" --model "$HOME/TTO/models/真实冻结模型.json"
```

除了配置通过，还要看到 `"model": "valid"`。如果显示 `unavailable`，先找维护者处理；配置检查通过不等于模型也可用。

确认文件正确、两路数据可用且本次观察窗口已经确定，再执行：

```bash
~/TTO/tto shadow --config "$HOME/TTO/config/local.json" --model "$HOME/TTO/models/真实冻结模型.json" --duration 1800 --episode "旁路使用01"
```

这条命令会联网，使用指定的固定模型观察30分钟，不在线训练，也不自动切换模型。需要积累最近3分钟的连续温度历史，期间预热或降级是可能的。

结束后，仍用第6节的 `report` 命令生成报告。报告使用本次当时保存的预测和评分，不会拿后来换上的模型重新算历史成绩。下一次要用新模型时，结束本次TTO，再指定新的模型文件；保留旧模型与旧记录。

## 9 一次测试结束后交回什么

用文件管理器把以下项目压缩在一起，交回完整一轮，不只挑看起来效果好的片段：

1. 本次 `run-…` 文件夹，完整保留。
2. 本次报告文件夹，包含HTML、Markdown和JSON。
3. `~/TTO/installation.json`。
4. 填好的“测试记录模板”，说明使用过程、起止情况及看到的提示。

原始观测、预测、评分与事件文件不要修改或删除。认证文件、密码、整个Conda环境不需要交回；也不要把私有任务内容写进场景名或测试备注。需要注明现场源服务版本、配置或模型版本时，写能确认的事实，不清楚就填“未确认”。

## 10 常见问题

| 遇到的问题 | 先怎么做 |
| --- | --- |
| 找不到 `~/TTO/tto` | 确认安装是否完成；若用了自选目录，使用实际安装目录里的 `tto` |
| 配置格式不对 | 检查编辑过的两处地址及采样周期字段，保留英文双引号和逗号，再跑离线doctor |
| 能开WebUI但TTO读不到 | 浏览器能访问页面不代表状态接口或Orin监控通道可用；保存提示和本轮文件夹，请维护者核对地址、接口与当前源版本 |
| 提示授权失败、401或403 | 结束本轮并保留记录，请维护者核对本机认证配置；不用在URL里加密码 |
| 提示证书错误 | 请维护者配置设备证书的信任文件，保留连接证书检查 |
| 另一个TTO观察进程正在运行 | 回到原终端结束那一轮，等它停止；不要同时开两轮观察 |
| 一直提示数据暂不可用 | 核对Orin是否产生有效新数据、两路服务是否可访问；不要将旧缓存算成新测量或修改源频率 |
| 没有模型成绩或M1降级 | 查看预热、采样周期、风扇状态、缺项和未来标签原因，照实交回 |
| 日志齐全但一部分评分被排除 | 属于当前评价资格变化，不是“文件缺失”；保留旧段与恢复后的数据 |
| 磁盘空间不足或提前停止 | 保留已写记录和停止原因，先归档已有资料；不要删除本轮证据后重跑冒充原测试 |
| 报告目录已存在 | 用新目录名再生成，保留旧报告 |

## 11 随手查的几个词

| 词 | 简单理解 |
| --- | --- |
| TJ | Orin芯片结温，是本软件预测目标；不是机壳温度 |
| PWM | 风扇控制百分比，不等于测出的RPM转速 |
| run | 一次命令录制生成的文件夹 |
| 场景名或episode | 你给持续使用过程起的短名字，帮助确认分组 |
| 片段或segment | 软件按数据连续性与质量自动划分的部分，不用你手动编号 |
| 基线 | 简单参考预测，用来判断复杂模型是否值得用 |
| shadow或旁路 | 固定模型只观察和预测，风扇控制照常由TianshanOS负责 |

第一次操作时，按第2到第6节走完并交回资料就够了。安装身份、现场连接、数据质量和预测效果是几件不同的事，分别看对应的记录；当前真实预测效果仍待数据验证。


## 读报告时先看这四件事

1. **数据有没有到**：有效新TJ样本和具名输入覆盖。报告里的分母是收到的有效新TJ样本，不把缺GPU的样本悄悄删掉。
2. **平台是否确认**：Orin/Thor声明来自远端设备树；观察器电脑身份另列。未知平台继续保存数据，但不能冻结已知平台模型。
3. **当前控制是否合格**：AUTO和CURVE分别统计。CURVE使用成功PWM，无需AUTO的gain；控制温度无效、实际来源仍default或人工模式时，都不能建模。已配置绑定不等于已生效，不要为了通过测试改风扇模式或绑定。
4. **模型证据是什么**：采集报告、离线留出评估、实际旁路报告分别标明。旁路读取当时保存的预测/评分；换一个模型文件不能改变历史成绩。模拟结果只证明软件链路。

如果收到TJ但GPU不可用，先保留记录和原因；如果温度状态无效，报告会提示现场来源需要核对。两种情况都不等于采集软件完全失效，也不能解读为可以降低风扇档位。

旧run默认按旧合同报告。要在一个新目录补充新版输入诊断，可执行以下离线命令；它不会替换原预测和评分，也不连接设备：

```bash
~/TTO/tto report --run /已有记录目录 --output /新的报告目录 --diagnostic-input-v2
```

本候选完成软件适配与离线验证后交回复审；新候选实机验证和真实预测效果另行安排。以上现场命令需要用户在安排好的现场窗口执行。

新版源周期与已有非空人工值冲突时，TTO保留原配置和数据，明确提示配置冲突并暂停模型资格；先核对两者来源，不自动改采样频率。GPU读取周期单独显示，不能当作源周期。
