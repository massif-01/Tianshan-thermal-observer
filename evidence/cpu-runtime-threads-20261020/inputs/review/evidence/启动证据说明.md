# 启动条件核对（原件身份见04来源清单）

## 本轮实际启动脚本
`evidence/field/run-once-remote.py`构造独立prefix的`tto-cpu-pilot capability`参数后，调用：
```python
p = subprocess.run(argv, stdout=out, stderr=err)
```
没有传入单独的`env`，没有显式设置BLAS线程数。该事实不能排除从父环境继承了某个设置。

## 旁证的范围
`evidence/field/interpreter-dependency-identity.json`的`current_readonly_shell_environment`中OPENBLAS_NUM_THREADS、OMP_NUM_THREADS、MKL_NUM_THREADS、NUMEXPR_NUM_THREADS均为null。
同文件明确写明：这是事后另一个shell进程的读数，**不能作为失败进程的实际环境快照**。

## 当前候选自身
本目录runtime摘录为cpu.2 wheel的原字节；observer-spec中CPU_BLAS_threads=1只是声明。cpu_cli、runtime和verify-install没有在该CLI链落实或核对实际数值线程池。

## 旧指导资料
旧现场操作卡的diagnose和execute示例在命令前写`OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1`。这是既有启动约束的证据，不证明已结束的每个现场进程均有效采用了此设置。

## 本轮新独立验证
使用同份Pipeline、原生engine、I-02、observer与39条原始事件，按原时间差回放12秒，不建立网络/Requester/SSH，也不启CPU旁录。四个独立子进程顺序是single1、default1、default2、single2。见results/blas-probes。
这里只变更各子进程自己的数值库线程环境，原wheel、模型、记录和阈值未改。主机/数值库与现场不同，不能当成N305修复验收。
