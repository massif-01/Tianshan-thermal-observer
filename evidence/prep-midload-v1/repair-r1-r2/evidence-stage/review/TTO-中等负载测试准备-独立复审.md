## 4. R1 / P2：无有效新TJ，却仍准许运行负载

**位置：`scripts/thermal_trials/health.py:24–42, 59–68`；消费者为`trial.py:39–55`。**

### 根因

`latest_source`只在`q['accepted']`为真时更新，这一半是对的。但计算有效截止和年龄时使用的是当前`engine.q.anchor_t/anchor_age`。当前质量器在新消息元数据有效、唯独TJ缺失时，会更新这组消息锚点，再返回`accepted=false / stale_or_missing_tj`；此分支的`blocked`未必为真。

结果是健康层组合了**以前的有效数值＋被拒绝新消息的时间**。它没有把mandatory TJ拒收或源资格边界打断为缺口，近期60秒连续标记也没有重建。

这不是源质量器把坏TJ送进了模型；源质量器仍正确拒收。问题是新增runner健康消费层将“没被blocked”等同于“仍有连续可信输入”。不需要修改上游源质量器或风扇。

### 独立反例

仅使用候选生产`PlatformEngine`、`TrialHealth`和包内原有合成消息生成器：0～70秒TJ有效；71～131秒新序号及fresh元信息照常到达，但每条缺少TJ；fan/temp保持正常。无网络、无设备访问。

| 时刻 | 源质量结果 | 最后真正接受的TJ时刻 | current_ready | continuous_60s |
|---|---|---:|---|---|
| 70 | new_sample | 70 | true | true |
| 71 | stale_or_missing_tj，拒收 | 70 | **true** | **true** |
| 131 | stale_or_missing_tj，拒收 | 70 | **true** | **true** |
| 132，恢复首帧 | new_sample | 132 | true | **仍为true，未重新累计** |

进一步将同一错误健康状态交给真实`run_schedule`，配合注入时钟与只记录调用的请求替身：在131.1秒，调度器确实调用了请求器，尽管最后有效TJ仍在70秒。实际请求数是替身调用数，未发HTTP推理请求。

### 影响与最小修正

本来应只保留准备数据或暂停新请求，实际却可能执行后续负载，既违背启动条件，也可能让用户浪费一轮测试。没有据此声称风扇停止、设备过热或硬件保护失效。

- 有效数值、源身份与其有效期必须归属于同一份实际接受的源观测；拒收消息不能为旧值续龄。
- 用现有源质量结果正确处理缺TJ、源有效性/身份边界、断连及恢复。正常重复缓存不能算新测量，也不能延长自身有效期。
- 缺TJ立即撤下本轮current-ready；旧数据可留作显示与追溯，不用于新负载准入。恢复首份有效输入只恢复当前资格，严格连续60秒必须按真实恢复后的记录重建。
- 保留功耗、成功PWM、温度状态等各自资格；不放宽TTL，不伪造数据，不永久锁死普通可恢复缺项。原明确保护/失温等锁停规则保留。
- 补`生产Engine→TrialHealth→run_schedule`交叉测试，证明缺TJ期间请求数为0，恢复前缀不足不能开新工作块，完整恢复后可按原合同继续；无需全仓故障矩阵。

证据：`scripts/check_health_source.py`、`scripts/check_readiness_to_request.py`、`results/health-missing-tj.json`、`results/readiness-to-request.json`。

## 5. R2 / P2：新测试入口可能加载旧TTO，预览却发现不了

**位置：`docs/TTO中等负载测试操作卡.md`第2、3步；`run_midload.py:40–46, 111–119`；与`install_tto.py:37–43`隔离launcher对照。**

原`tto` launcher使用`python -I -m tto`，新操作卡却使用`conda run ... python /路径/run_midload.py`。这个新入口会继承`PYTHONPATH`；runner在live才导入并核验TTO，离线plan不核验实际导入。版本不符被main最后的通用ValueError分支改成了“配置不完整”。

### 独立反例

- 新临时环境非editable安装本次0.2.3，23份内容已核对。
- 将真实旧0.2.2源码（由本次patch反向恢复）设置为`PYTHONPATH`，模拟已有开发环境残留，不使用恶意模块。
- 使用与操作卡相同的非隔离脚本启动语义；给出仅loopback的完整合成配置。额外阻断并计数所有socket连接/解析。

| 操作 | 结果 |
|---|---|
| `--plan` | 退出0，预览成功 |
| `--live`入口检查 | 实际导入旧0.2.2，退出2 |
| 用户提示 | “本地配置不完整或不可用；未启动测试。请按操作卡核对配置路径。” |
| 网络尝试 | 0 |

没有在本轮实际运行Conda；复现的是它调用的Python脚本入口及相同环境变量导入行为。版本门槛确实拒绝了旧程序，因此没有“旧采集器已偷偷跑完整轮”的结论；确认的是安装/预览成功仍不能保证正式入口使用新版本。

### 最小修正

给runner提供与已验证安装环境一致的隔离入口，操作卡调用同一入口。**不能机械加`-I`后破坏`from trial/health/requester`等兄弟模块导入**；使用限定于本包目录的引导或适当的包入口，并验证实际TTO导入路径。

离线检查可核对本地版本/入口身份，但继续保持不访问端点、不读取鉴权文件。版本/导入错误应明确提示实际加载版本、正确入口与下一步，不统一归咎配置文件。补真实旧PYTHONPATH下的干净安装、plan与loopback运行测试，保留取消和归档行为。

证据：`scripts/check_runner_import.py`、`results/runner-import-path.json`。这只是新runner入口的收尾，不要求重构Conda安装器或增加安全平台。
