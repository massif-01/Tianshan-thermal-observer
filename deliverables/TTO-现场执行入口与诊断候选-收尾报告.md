## 2. 真正接通的数据与生命周期

入口只接受显式配置、当轮绑定文件和`--allow-network`。预览无此开关、无网络客户端、不打开认证头。没有默认设备地址，不做发现，不加载模型。

实际执行链为：

```text
唯一collect() / Journal分配实际UUID
  → native engine.process一次，原始record/out/engine回调
  → #9 I-02派生视图 + #8只读投影（共享该结果，不再处理一遍quality）
  → 冻结ThermalObserver
  → 带真实生成时刻/截止的现场信封
  → 分层门控 / 原Scheduler
  → 唯一执行器拥有的1/2/4个Requester槽位
  → 原始记录、状态、请求、阶段和收尾索引
```

没有第二个轮询器。`projection.py`只把原SavedStream改为接收现成engine及processed结果；数学实现未动。I-02桥接器对原专项脚本作依赖注入：其`engine_for`得到一个只返回当前已处理结果的只读view，生成器仍执行原专项的生命周期逻辑。不是再建一个质量引擎，也没有重写专项修复。原脚本字节相同，桥接前后有效性另列；native原始记录与原quality输出不改。

实例证明不是只写`collector_count=1`：最终7场景各有且只有一个native run目录；每条原始ref和状态均关联该目录的实际UUID；native engine实例ID与I-02共享实例ID一致，I-02 processed-view次数等于native回调次数，observer只创建一次。检查了505份字段链文件及49份native文件的已有SHA索引，全部一致。

原生Journal在创建时生成UUID。启动授权先绑定唯一command_id和模式；首条native记录将该命令意图绑定实际UUID，并落盘native-binding.json。调度、请求及测量随后均用实际UUID，不能把前置命令登记中的意图别名当成测量run UUID。不同run不会拼接。

只读诊断由总控未来单独运行；混合执行由原“模型推理监控”对话01a1331a-f937-7d91-aef0-ac4f5e50bd8a启动唯一命令，其一个进程同时管理采集和请求，总控不另发API。没有新建总控层。

## 3. 时钟与当前有效性

源采样/源接收时间继续留在原始payload及native新鲜度证据内。native row.mono_s是该进程接收/入队时的同主机单调钟；投影/估计传播至这个观测截止；实际估计完成以后，再读取本进程monotonic和UTC记录生成时刻。

现场信封另外记录：

- 同主机时钟域：hostname、PID及本轮随机域标识，起止各有mono前/UTC/mono后括号；native manifest也登记该域。
- `observer_input_mono_s`：原record时间，不用读文件或写状态时刻重打。
- `generated_at_mono_s/utc`：实际回调完成估计后的读取时刻。
- `model_consumable_until_mono_s = min(生成时刻+2.5秒, 原观测截止+2.5秒)`：本候选登记的**状态消费新鲜度上限**，不是传感器TTL、预测有效期或安全保证。
- 每项TJ/两rail/成功PWM/控制上下文的原始引用、observed/age/expiry/raw_valid不因生成信封而续龄。I-02生命周期撤销与native投影原标记分别保留。

研究实现的快照仍带原固定offline_virtual_observer_clock文字，原件不改；它不被现场门控当成主机时钟证明。现场依据是实际native回调、实际monotonic读取、同进程域绑定和上述独立截止，不是把旧文字换名后宣布live。估计传播截止与估计真正生成时刻明确分开。

异步消费者允许生成时刻早于当前评估时刻，不再要求严格相等。每约0.1秒独立唤醒评估，即使没有后续消息也会到期、暂停新请求或按60秒上限终止。这里不支持把另一台主机的旧状态文件直接喂入；若未来分离进程/主机，需另做明确钟域映射，不能靠聊天时间或温度曲线拟合偏移。

四层判断仍分开：当前测量、条件模型状态、保护/模式/绑定、当前授权及仪表。finite/provisional不能自动放行；unknown保护不写成false。模型原permission一直是研究只读，不被提升为设备许可。许可来自本次命令的显式绑定，仪表首锚点还要核文件SHA、时区、显示分辨率及未知误差声明。

## 4. 两种可运行模式与固定政策

### A：diagnose / readonly-diagnostic

默认记录300秒，允许更短的有界诊断。**不实例化Requester、不访问模型列表或推理接口，不要求模型tracking或仪表记录才采事实。** 即使当前估计不可用，仍保留原始诊断和具体原因。

记录同一collector的fan/temp阶段、原2秒预算内RTT、成功fan间隔和超过2.5秒的次数、真实到期、来源及估计状态、保护/配置身份、CPU/RSS和日志字节。TJ/独立rail/GPU利用率/成功PWM/gain/斜率/预测/失温等仍在原始记录里，不丢字段。

输出diagnostic-precheck.json、按秒累计的测量/模型/上下文资格、phase_seconds及原因；按约0.1秒网格积算，属于有明示评估粒度的近似时长，不是事件条数百分比。结束前最后一次资格不代表下一次B仍然合格。5分钟无超时不证明历史根因修复；A不自动升级B。

### B：execute / fixed-anchors

没有删除raise就交付。B实际构造collector、原生质量投影、估计器、独立到期循环、原Scheduler和实际Requester；先只读核驻模和现有运行/排队计数，不负责拉模型。当前配置、collector/model/spec、当轮明确许可、仪表记录/固定/首锚点、当前输入与保护分别满足才发请求。

首轮固定原RM-01 VLM / 历史27B稠密模型。原模型payload、max_tokens256和30秒协议预算保持；须登记当前路径/引擎/模板/缓存和客户端4槽位容量证据。完整权重或固件二进制哈希未知可以保留未知，不扫描大权重或伪造身份。容量不符先拒绝/说明，不偷偷扩超时。客户端1/2/4不是服务端执行数。

固定计划不变：背景300→单路360→回落90→双路270→回落240→四路450→回落120→同单路360→最终回落480秒。名义2670秒（44分30秒），准备300、四块drain各最多90、清理120，保守3450秒，上限3600秒。硬限前120秒停止后续工作，清理预算包含在内。窗口是发起窗口，关窗后自然drain再进入回落，不强断当作完成，不按暂停时间补跑。

5秒上下文确认和#8原数值/输入政策不变；fan2.5秒、temp7.5秒及源TTL不改。**60秒连续不可准入上限现按收尾合同固定执行**，不再留给下一对话决定；它不是初始化要求、TTL或安全保证。随源保留的旧plans/execution-policy.json是历史准备文案，实际入口执行的是本节和runtime.py已固定政策，不使用其中旧“待开放模板”状态。

当前必需测量/保护/估计不合格立即暂停新请求；明确guard/fault/禁用、非AUTO/手动、绑定/不允许来源改变，以及用户停、硬预算、请求结束未知按原有界收尾。协议超时、取消、不完整SSE都保留服务端未知；不继续排请求掩盖它。

`schedule_completed`与`work_paused_s`、实际请求日志分别报告。暂停较多即写completed_with_pauses_review_exposure，不能仅凭completed称负载意图实现。AUTO、曲线、gain机制、保护、功耗模式、采样及原质量规则均未改，未继承旧M/Y override。
