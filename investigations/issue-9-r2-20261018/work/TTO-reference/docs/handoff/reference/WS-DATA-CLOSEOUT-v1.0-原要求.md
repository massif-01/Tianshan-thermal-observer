## 2. F1：补齐读取线程未启动时的资源清理

### 2.1 原问题及范围

上轮候选把输出管道的关闭放在读取线程的 `finally` 中。当 `Popen` 成功、但线程构造或 `Thread.start()` 在读者尚未启动时失败，这段 `finally` 不会执行。

已确认的表现是：子进程可以被回收，状态为 `error`、`fresh=false`，但 `stdout` 未显式关闭，并可能继续被未启动线程的参数持有。它不是正常采集中的无限泄漏，也不是旧信号死锁复发。

### 2.2 修复要求

保留现有生命周期隔离，只补明确的资源所有权缺口：

1. 明确区分“读者未成功启动”与“读者已经接管输出管道”。只在确认没有读者持有管道时，由失败清理路径接管关闭责任。
2. 对子进程创建后的线程构造失败、线程启动失败，回收对应子进程，并显式关闭仍归启动方所有的输出管道。清理由本次生命周期的对象执行，不能误关后来重启产生的新管道。
3. 清除不再需要的本次失败线程/进程引用，不依赖垃圾回收或解释器退出代替资源清理。不要修改 `Thread` 私有字段来强行释放引用。
4. 保留原启动异常、`error`、`fresh=false`、无首帧语义；重复 `stop()` 不把错误改成成功，不制造重复回收或新异常。
5. 正常读取、EOF、读取异常和停止仍沿用正确的读者清理，不在主线程中随意关闭另一线程正在读取的流。不单凭某一瞬间 `is_alive()==false` 就推定从未启动。
6. 保留退出意图与延迟清理机制，不能为了关闭管道重新在信号处理器中调用阻塞清理，也不通过改成可重入锁、忽略信号来掩盖问题。
7. 清理异常应有真实、有限的诊断；不能掩盖最初启动错误，也不能在资源尚未回收时记录“全部清理成功”。

不增加自动重启策略、线程池、通用进程监管框架或无界重试。

### 2.3 最低验证

必须用生产解析器执行断言。仅替换采集命令、时钟或故障注入点：

| 场景 | 必须验证 |
|---|---|
| Popen成功，线程构造失败 | 子进程已回收、stdout已关闭、error/fresh正确。 |
| Popen成功，Thread.start在读者启动前失败 | 同上；保持外部测试引用、不主动GC时，也已经关闭。 |
| 失败后重复stop，再启动一次正常采集 | 无重复清理错误；新stream不混入旧数据；新读者能正常读取。 |
| 正常读取、EOF、停止及原旧线程迟到 | 没有抢关正在使用的管道，没有污染新生命周期。 |
| 原七类CLI信号场景 | 旧死锁不复发；退出码、状态和回收行为继续符合原断言。 |

至少一个失败场景使用受控的本地Python假输出子进程与真实管道，不能只在一个预设 `closed=true` 的模拟对象上证明关闭。测试子进程必须有超时和回收；不得运行真实 `tegrastats`。

## 3. F2：修好真正的启动配置，不仅提醒部署人员

### 3.1 原问题

当前候选 `cli.py::run()` 从 `Config()` 起步，只应用CLI参数。虽然 `Config.from_env()` 存在，但启动入口未采用它。当前 `config` 子命令也只显示 `Config()` 的默认值。

因此，只给环境变量设置 `TEGRASTATS_API_TEGRASTATS_INTERVAL=3000`，CLI实际仍可能运行 `tegrastats --interval 1000`。用户现在要求改变这一既有行为，不能继续以“部署时留意”为完成标准。

### 3.2 冻结解析顺序

对每个现有配置项，统一为：

**用户显式传入的CLI选项 > 项目现有主环境变量 > 项目现有旧环境变量别名 > 内置默认值。**

适用规则：

- 仅显式CLI参数覆盖环境；CLI的默认值不能冒充用户选择。
- 从候选来源中先选定生效值，再对该值归一化/校验；被更高优先级覆盖的无效低优先级值，不能先报错挡住合法显式配置。
- 高优先级被选中但非法时，清楚报错，不能偷偷回退到低优先级。数值、布尔和主机地址等不允许的空值也应按此处理。不要打印整个环境。
- 主环境变量与旧别名都存在时，主变量优先；没有主变量时才使用既有别名。不得自创、改名或删除别名。
- 不把 `Config()` 隐式改成对所有调用者自动读取环境。保留显式 `Config(...)` 的可预测性；为CLI和配置预览复用同一个小型解析入口，并与 `Config.from_env()` 的规则一致。
- 不引入 `.env` 自动加载、YAML配置平台、远程配置或热更新框架。

**不能只把 `Config()` 文本替换成 `Config.from_env()` 就结束。** 还要处理布尔开关、优先级、非法低优先级输入和配置预览，否则仍可能“看似改了、实际不对”。

### 3.4 类型、单位与布尔值

- 采集间隔继续为正整数毫秒；`1000`和整数等值`1000.0`都归一化为1000。Parser保留严格正整数int校验。不得默默乘1000。
- 推送间隔是秒，保持现有合法小数输入，但须为有限正数。零、负数、nan/inf不得进入睡眠或发送循环。
- 端口、连接数等按其既有用途验证合法范围；不能让配置错误进入监听或采集阶段才暴露。
- 环境布尔值明确支持大小写不敏感的`true/false`、`1/0`、`yes/no`、`on/off`，前后空白可去除；其他选中值报错。不能使用 `bool("false")`，也不能把任何拼错文本静默当false。
- `--debug`保持兼容，并提供明确关闭方式，例如`--no-debug`。不传开关时保留环境值；显式关闭能够覆盖环境true。两种开关同传时，行为需明确并有测试。
- 日志级别按已支持集合和大小写规则归一化；选中的非法配置应在生产服务构造、采集和监听前退出，CLI错误说明字段与来源，保留技术排错信息但不输出凭据。
- `--help`和版本帮助不应因为无关的坏环境变量而启动服务或失去可用性。

### 3.5 用户能够知道“到底用了什么”

启动时输出一份简短的最终配置摘要，至少包含监听地址/端口、采集间隔（ms）、推送间隔（s）、新鲜度阈值、debug，以及关键值来源。摘要必须来自即将传给实际服务/解析器的同一份配置，不另外算一遍。

例如以下只是新要求的格式示意：

```text
采集间隔：3000 ms（来源：TEGRASTATS_API_TEGRASTATS_INTERVAL）
推送间隔：1.0 s（来源：内置默认）
数据过期界限：9000 ms
```

`config` 子命令应复用同一解析规则，并能按与启动相同的相关选项预览配置。明确标注“本次环境与参数对应的启动配置；未查询运行中的服务”，不能把默认值或当前终端环境称为systemd进程的实时设置。预览不能创建采集进程、启动ModelMonitor或监听网络。

systemd服务与用户终端可能使用不同的环境、命令行或安装路径。因此，最终部署说明仍需核对服务实际收到的配置；但不能把这句话当成继续忽略环境变量的借口。

走真实Click入口、配置解析、生产服务构造和生产Parser路径；采集进程与监听用替身。不是只测试 `Config.from_env()`。
