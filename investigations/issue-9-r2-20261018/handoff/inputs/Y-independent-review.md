# TTO / YET-610L同步短问答：独立复核与项目判断

审查日期：2026-10-18。唯一新run：`1ae9a7d7-bec7-4e45-a9d6-4415b4a8dece`。

## 1. 结论

真实局部表面记录已经取得，CSV与请求执行证据可以保留；原定的“冻结G2慢态与局部表面比较”尚未完成。三套G2在现有严格规则下都未获得60秒初始化前缀，合法数值状态为0。不是模型算出很差的误差后被弃用，不是模型误差为0，也不能说明G2优于或劣于LP30。

这轮最重要的新瓶颈是实际可用性：对风扇状态的获取存在大量超时/新鲜度空隙；现有研究协议每遇这类空隙便重新等待连续前缀。模型方程、测温工具和之前L/S/M的成绩不因此被推翻，但现有组合还不是适合真实间歇遥测的连续热观察器。

建议：先用已有数据完成有限的输入可用性和状态连续估计研究，并针对fan/status读取做小范围核对；然后进行用户建议的更长负载、不同并发、不等间歇实验。不要直接把下一轮负载加长，也不要修改旧TTL/评分来把当前0状态变成一次假成功。

## 3. 新增确认：模型未启动主要不是三个红叉

源自原始`observations-0001.jsonl`，不是把边界计数当作故障次数：

| 原记录对象 | 独立计数 |
|---|---:|
| fan/status请求 | 1256 |
| 成功返回 | 1029 |
| TimeoutError | 227（约18.07%） |
| 相邻成功返回间隔超过2.5秒 | 349 |
| 相邻成功返回最大间隔 | 4.0394秒 |
| 成功fan快照里的temp_stale=true | 3 |
| 成功fan快照里的mode | 全为AUTO |
| 成功fan快照里的guard/fault | 均false |
| temperature status请求/成功 | 370/370 |
| temperature status里valid=false或active_source非variable | 0 |
| Jetson源epoch | 1个，1843条accepted均在其中 |

349个返回年龄空隙与227个超时并非同一计数，也不能相加。每个“间隔超过2.5秒”的未知尾部约0.0028—1.5394秒，累计约364.922秒；这只是成功快照年龄支持的算术描述，不等于精确硬件异常持续时间。仅并集“成功返回后的2.5秒可见窗口”，最长也只有33.023秒，仍没有60秒。

原生模型严格段最长26.013秒，当前完整输入约1337.594秒、72.4%，但没有连续60秒。软件的`input_profile_change`等计数含输入从已知变未知再恢复，不能当作反复更换芯片/平台/真正改配置。原生源/控制/输入边界计数存在重叠。

这证明应将当前瓶颈具体称为“风扇状态读取与研究初始化连续性”，不应笼统称为仪表不准、TJ没采到，或只是偶发三个红叉。它不确定超时发生在网络、浏览器刷新并发、接口等待、锁或其他环节；本轮没有追查这些根因。

与旧M的fan2508次全部成功相对，本轮的实际路径明显不同；两轮环境/行为并未控制一致，因此不归因于单一代码退化。

| 稀疏 | 466.069秒 | 6 | 12.830秒 | 2.75% |

合计39.231秒。它是客户端协议在途，不是GPU内核精确忙碌时间。独立遥测算术均值中，稀疏GPU利用率约2.35%，连续组约16.92%；对应GPU rail均值约2.480W和5.659W。阶段平均包含任务与空闲，不当作请求执行时纯功耗。

## 5. 真实表面带来了什么信息

- 仪表CH1为靠近出风口的一处鳍片表面，38.51—39.94°C，振幅1.43°C；TJ为43.718—48.937°C。不是同一温度量，也不能将两者之比解释为热容。
- 按名义UTC+8对齐，稀疏段表面均值38.827°C、范围38.52—39.48°C；六次TJ短峰对应局部表面总体下降并有下探—恢复走势。
- 连续组表面均值39.205°C、范围38.99—39.40°C；最终600秒阶段表面均值39.755°C、范围39.41—39.93°C，TJ先降到较低水平，表面仍缓慢上升。
- 本次成功PWM快照：稀疏16—29%、连续17—28%、最终回落17—26%。没有用未知间隔延续旧值来计算全时风量，也没有RPM或噪声测量。

一种值得验证的解释是：短任务引起局部TJ与风扇反应，探头所在出口侧薄片更直接受到局部对流冷却；任务结束后普通风量降低、内部仍有热传递及背景热源，于是该表面可继续升温。这个解释与记录相容，但不是本轮已辨识因果；热前史、未测环境、其他共享热源和探头接触/响应仍未分离。

不能由表面下探推断短任务无热量，也不能宣布風扇一定过强；不能由结束后升温就决定应把风扇维持高档。需要模型或实机对照检验，不靠曲线观感决定控制。

## 6. 时钟证据的适度使用

两张同框照片有独立信息：历史开始附近仪表00:17:24/网页00:17:26；结束附近仪表01:03:15/网页01:03:16。结束图已直接查看。历史图早于本次run且用户确认期间未重新校时，因此不能当本次开始瞬间，却也不能说完全没有任何历史对应依据。

它们尚未给出网页刷新/主机时钟链/采样时刻的完整误差界，所以不硬设固定+1秒/+2秒，不宣称精确漂移。原报告的“严格配对0”是严格资格结果，不表示仪表没有日期时间或分钟尺度曲线必须扔掉。

原0及±5/±10/±30秒情景可以保留为敏感性，不称误差界，更不挑最贴合一项。本轮只支持标注近似的阶段/趋势说明，不能用来识别精确秒级滞后或排0.01°C级胜负。

下一轮优先让仪表底部运行时钟与采集主机的持续跳动时钟同框，在开始/结束各留一小段记录，保存时区及可观察的不确定性；不用聊天响应时刻作采样锚点，也不按温度曲线校时。开始/结束按键不必同时，保证覆盖和独立时间对应即可。

## 7. 对更长、更多并发、不规则间歇建议的判断

支持用户提出的单路5—10分钟、双并发3—6分钟、四并发5—10分钟。新增价值是持续加热、热前史和不同阶段的累计响应；与原规则短脉冲互补，不替代全部可重复对照。

需要三个修订：

1. 用预先固定的不等工作时长/不等休息，或固定种子的有界安排；不是现场临时随意改一切。预测器不读取未来排程。
2. 并发数不是热功率。过去L单路与四路GPU rail约26.25/27.59W，已经很接近。下一轮保存客户端在途数、可取得的服务端执行/排队证据、实际功耗及吞吐，不把提交4路叫4倍热负荷。
3. 最好保留一次同类型单路块在不同热前史后重复。否则1→2→4的差异同时含并发、时长、前序储热和自动增益变化，无法单独归因。

建议组织形态是“背景→长单路→短歇→双路→较长歇→四路→另一种回落后重复单路→最终回落”。具体时长、请求上限和自然完成预算应在新实验计划里冻结；目前不是现场执行授权。不能用无限重复请求凑指定温度，也不在客户端截止时假定服务端计算已结束。

## 8. 唯一优先动作与分工

### 先交建模对话：原规则封存，做一次有界状态可用性实验

本轮先不重训θ、不扩大模型族，不用外部CH1纠正状态。将以下东西拆开：

- 测量是否真实新鲜；
- 热状态是否仍能带条件估计；
- 控制情境是否确认正常；
- 是否允许模型输出影响风扇。

有真实成功PWM而只是控制源/模式标记改变，不等于热体状态清零；数值输入真正未知则必须显式处理输入不确定性，不把最后值延长成真实测量。

新方法必须同时解决“已有状态遇短缺口如何保留/衰减信任”和“从启动起一直没有完整60秒时如何建立有不确定性的初态”。只增加短缺口后的延续功能，不能解决本轮从未初始化的问题。

先拿旧M完整段，按本次缺口形状遮去辅助输入，用未遮挡记录核对信息损失、偏差、恢复和输出覆盖；该完整记录只用于检查，不流入有缺口的因果估计器。完整数据生成的Ts也只是参照估计，不是物理真值。新数据派生结果必须标新诊断合同，不覆盖352段/0状态原结果。可信度不足可以不输出，目标不是保证每秒都有一个数。

标准状态估计可区分模型传播和测量校正；但本例缺的是控制输入PWM，不能仅靠“跳过校正”假定问题自动解决。对未知输入、初态和边界要有明示假设/范围及可验证的不确定性；具体方法另在执行规范里确定。此轮仍不是在线参数学习或控制授权。

### 测试对话：并行准备最小采集修正与新负载计划，不立即长测

只围绕fan/status请求频繁超时、成功快照新鲜度检查已有日志、现场版本/调用路径及状态接口；不重新全仓审查风扇算法。下一轮开始前应能展示近期热模型状态是否已形成或新估计器是否达到自己的就绪条件，而不只展示current_ready一瞬间正常。失败时保留准备数据，不让用户再跑完一小时后才被告知全程0状态。

### 两者准备好以后：一次新混合长负载同步记录

用户用已有YET和同一测点记录。AUTO、曲线、gain更新机制、保护不改；新环境温度能取得则单独记录，不能复制旧M的24°C。先冻结候选在新记录上评价，再另行决定是否纳入训练。潜在状态校准、连续估计、参数在线学习和风扇控制仍分阶段推进。

结论：本轮仪表和真实温度资料不是白做，但物理对照目标未达成。短时数据缺口不能让热观察器每次都失忆，准确性也不能靠伪造数据获得。先完成这个工程台阶，再用更有信息的长/短/并发混合工况检验模型，才是在朝通用TTO前进。
